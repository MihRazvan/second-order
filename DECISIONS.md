# Decisions

Format: decision, why, rejected alternatives. Newest at the bottom. Dates are absolute.

## D-001 · 2026-09-04 · Browser-side CrowdGuard
**Decision.** The capacity surface is derived in the browser from the same normalized events the server sees; the user's intended size, delay assumption and policy thresholds never leave the browser.
**Why.** The brief makes this a hard privacy constraint, and the model is cheap enough (bisection over an interpolated grid) to run per keystroke.
**Rejected.** Server-side verdict endpoint (would require sending intended size); WebAssembly build of core (unnecessary for this compute budget).

## D-002 · 2026-09-04 · Sparse quote grid + interpolation instead of 100 live quotes
**Decision.** Observe quotes at a small set of (delay, size) points and interpolate; extrapolate with a calibrated constant-product term flagged `extrapolated`.
**Why.** Firing 100 simultaneous quotes is dishonest about what was observed, wastes credits (quoting is 1 credit/min plus per-quote cost) and would still not cover the crowd-AUM axis.
**Rejected.** Dense quote sweeps; pure closed-form AMM model with no observations (loses the "live witnessed" claim entirely).

## D-003 · 2026-09-04 · C(delay, crowd AUM) defined as remaining capacity behind existing flow
**Decision.** `C(d, A) = max X ≥ 0 such that EV(d, X | A) ≥ 0`, i.e. the maximum *additional* aggregate follower capital that remains scenario-compatible at delay `d` given competing flow `A` already in the route. Remaining Alpha is `C(d_user, A_now)`.
**Why.** This matches the brief's signature, makes the Remaining Alpha meter and the "maximum scenario-compatible size" the same quantity, and keeps the solver monotone (EV decreases in X).
**Rejected.** Defining C at zero crowd and subtracting A (loses the follower's own impact on the exit); defining C via a fixed representative follower size (hides that the user's own size matters).

## D-004 · 2026-09-04 · D3 primitives rendered as React SVG
**Decision.** Use `d3-scale`, `d3-shape`, `d3-array`, `d3-interpolate` for math and draw SVG in React components styled with the design tokens.
**Why.** The signature instrument is bespoke (a swarm plus a battery plus a surface slice); a chart library's defaults would define the identity, which the brief forbids. D3 sub-packages are small, tree-shakeable and have no theme.
**Rejected.** Recharts/visx (component-level opinions and default themes to fight); Canvas/WebGL (harder to make accessible and to screenshot deterministically; not needed for ~100 marks).

## D-005 · 2026-09-04 · Fixture package instead of raw JSON directory
**Decision.** `data/replays` is a workspace package `@second-order/replays` exporting the manifest and typed loaders, generated by a seeded script.
**Why.** Both `apps/stream` and the browser fallback need the same fixture with type safety; a package keeps one import path and lets Vitest validate fixtures against the contracts.
**Rejected.** Fetching JSON over HTTP from `public/` (duplicated files, no typing).

## D-006 · 2026-09-04 · Fonts: Archivo + Martian Mono, self-hosted via next/font
**Decision.** Archivo (variable, with width axis) for interface and display; Martian Mono for numerals, tabular data and evidence. Both are SIL Open Font License and are self-hosted at build time through `next/font/google`, so no runtime request leaves the app.
**Why.** The brief bans Inter/Arial/system/Geist and asks for a face that supports a laboratory/forensic register. Archivo's grotesque skeleton and width axis give condensed instrument labels and wide display numerals from one family. Martian Mono is a condensed technical mono with tabular figures that reads like recorder output rather than a code editor.
**Rejected.** IBM Plex (credible but ubiquitous in fintech); Space Grotesk/Space Mono (saturated in crypto); JetBrains Mono (reads as IDE, not instrument); Barlow (DIN-derived industrial look already common on trading terminals).

## D-007 · 2026-09-04 · PostgreSQL optional at runtime
**Decision.** Persistence is enabled when `DATABASE_URL` is set; otherwise the stream service runs in memory and reports `persistence: memory` in `/health`.
**Why.** The 15-second demo must not depend on a database being up; persistence exists to keep evidence and replays for judges and for capturing a live witnessed replay.
**Rejected.** Mandatory DB (fragile in a demo); SQLite (Railway target is PostgreSQL, one engine is enough).

## D-008 · 2026-09-04 · Impeccable and Chrome DevTools MCP availability
**Decision.** At session start neither the Impeccable skill nor the Chrome DevTools MCP server was installed. The Impeccable repository was cloned read-only and its `init`, `shape`, `new-work` and `craft-floor` references were followed manually. Mid-session the project gained `.claude/skills/impeccable/` (with its design-detector hook on Edit/Write) and a `.mcp.json` declaring `chrome-devtools` and `shadcn` servers; the skill scripts are used from that point, but MCP servers declared after session start are not reachable in the running session, so browser inspection uses Playwright-driven Chromium (already required for the e2e suite), capturing screenshots plus console and network logs at the three required viewports.
**Why.** The workflows and the inspection loop are reproducible either way; blocking on tooling would have stalled autonomous progress.
**Rejected.** Skipping the design process; pausing for a session restart.

## D-009 · 2026-09-04 · TypeScript 5.9, not 7
**Decision.** Pin TypeScript `~5.9` across the workspace.
**Why.** TypeScript 7 (the Go-based compiler) is the latest tag on npm but the Next.js/Drizzle/Vitest toolchains in use were validated against 5.x; a compiler migration is not a hackathon risk worth taking.
**Rejected.** TypeScript 7.

## D-010 · 2026-09-04 · Replay clock lives in the provider, not the UI
**Decision.** The replay provider emits events with the fixture's original relative timing (speed factor configurable); the UI only reacts to events. The "Crash test this wallet" button starts a session on the server (or in the browser fallback) rather than animating a script.
**Why.** Keeps the UI provider-agnostic: a live witnessed session and a replay drive identical code paths, which is the whole point of the provider abstraction.
**Rejected.** A UI-side scripted timeline (would make the live path a second implementation).

## D-011 · 2026-09-04 · Mobula's keyless demo API is the default REST backend
**Decision.** Without `MOBULA_API_KEY` the stream service talks to `demo-api.mobula.io`; with a key it uses `api.mobula.io`. Reconstructions therefore work on a fresh clone with no signup.
**Why.** Mobula documents the demo API as keyless and rate-limited for testing; it serves every REST endpoint the reconstruction needs. Judges can run a real wallet without provisioning anything.
**Rejected.** Requiring a key (blocks the first-run experience); bundling a key in the client (never).

## D-012 · 2026-09-04 · Redesign to a BIOS setup utility with Win95 dialogs
**Decision.** Replace the flight-recorder surface with a setup-utility world: navy field, cyan labels, bracketed values, Item Specific Help, block-glyph meters, function-key navigation, Win95 dialogs for CrowdGuard and the Evidence Log. VT323 + Archivo.
**Why.** The founder judged the recorder too close to a generic dark dashboard for a fifteen-second pitch and pinned this aesthetic with mockups. The utility metaphor fits the product exactly: a diagnostic you run before you act, with every setting explained beside it.
**Rejected.** Blending the two worlds; keeping the recorder as a secondary view (clutter without a job).
